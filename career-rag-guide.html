Two systems, not one

"RAG database that also searches for jobs" is actually two pipelines sharing one vector store. Worth separating cleanly, because they have different data, different refresh rates, and different queries.

Track A — corpus

Index what already exists

Embed the 90 application folders, the tracker, and the resume variants so you can ask things like "what did I tell Deloitte about the Bedrock gap" or "which cover letters used the Visa FIFA WWC story" without grepping 90 folders by hand. Refreshes once per batch.

Track B — matching

Score new postings as they land

Embed a freshly scraped job description, compare it against the resume + past-application vectors, and rank it by fit before anyone reads it. Refreshes every time vibatchium pulls a new batch of listings.

Both tracks read and write the same Chroma collection with a doc_type field distinguishing them — one store, one embedding model, two query patterns.

Architecture

One store, two write paths, one read path with a mode switch.

01

Inventory the source files, exclude what shouldn't be embedded

Walk the folder once, classify every file by the table above, and build the exclusion list before writing a single line of embedding code. Never embed _ats_credentials_*.md; also skip .DS_Store, binary PDFs (index the HTML twin instead — same text, no parsing needed), and the two template files (_template_resume.html, _template_cover.html) which are structure, not content.

02

Chunk by document shape, not a fixed token count

The default RAG move — split everything into 500-token windows — actively hurts here, because most of these documents are already the right retrieval unit. A NOTES.md is ~150 words and answers exactly one question ("was this a good fit and why"). Splitting it loses the thread that makes it useful.

NOTES.md, outreach.md → 1 chunk/file _tracker.md, LOG.md, RESUME_HERE.md → split on ## sections; a section that's a table further splits 1 chunk/row, leftover prose stays 1 chunk job.json → flattened to key: value lines, 1 chunk Cover_Letter.html, Resume.html, master resumes → HTML tags stripped (stdlib html.parser, no bs4), 1 chunk/file

Exception path, not the default: anything over 400 words (a long resume, a verbose cover letter) falls back to sliding windows — 400 words, 60-word overlap — so a chunk never gets so long the embedding blurs into an average of unrelated content.

Two cleanup passes run on every chunk before it's final: markdown noise gets stripped (**bold**, [text](url) links, em/en dashes — syntax, not signal, and it eats the token budget for nothing) — and tracker columns get normalized to one canonical set, since _tracker.md uses five different header sets across its batches (Angle taken, Gap named upfront, and Confirmation seen all collapse into one Notes field), so a query for "notes" or "salary" hits every batch instead of whichever one happened to use that exact column name.

career_index/lib.py — chunk dispatch, tested against the real files
def chunk_file(path):
    name, ext = path.name, path.suffix.lower()
    if name == "_tracker.md":           return chunk_markdown_sectioned(path, ..., "tracker")
    if name in ("LOG.md", "RESUME_HERE.md"): return chunk_markdown_sectioned(path, ..., "log")
    if ext == ".json":                  return chunk_json(path, ...)   # any .json, not just job.json
    if name == "NOTES.md":              return chunk_whole_file(path, ..., "notes")
    if name == "outreach.md":           return chunk_whole_file(path, ..., "outreach")
    if ext == ".html":                  return chunk_whole_file(path, strip_html(...), _html_doc_type(path))

Other things worth adding to chunking, roughly in order of payoff for this corpus:
  • Token-aware guard, not word-aware. The 400-word guard is a proxy — bge-small's real limit is 512 tokens, and markdown/HTML text runs ~1.3 tokens/word. A resume chunk at 400 words can brush the ceiling. Worth switching to counting tokens via the model's own tokenizer once step 3 (embedding) is wired up.
  • Parent-child linking. A tracker_row chunk is compact (~40 words) — great for a hit, thin for an answer. Tagging each chunk with an application_id that maps back to its full folder means a query can retrieve the row and pull in the matching NOTES.md/job.json for real context, not just the row alone.
  • Dedup near-identical chunks. Cover letters share a lot of boilerplate structure across applications. Not urgent at 90 folders, but if this scales up, embedding-similarity dedup before indexing keeps the store from being dominated by near-copies.
  • PDF/DOCX parsing. Still sitting in needs_parser untouched — only matters for the ~4 top-level resume variants with no HTML twin, so low priority.

Markdown-noise stripping and cross-batch tracker normalization are done — folded into the chunk dispatch above.

audited
Two independent reviews, run against each other. Two agents reviewed this file separately — different failure-mode focus, neither saw the other's work — then findings were cross-checked against the real code. Both independently caught the same high-severity bug, which is the strongest kind of confirmation; each also caught things the other missed. Six real issues fixed:
  • Credential exclusion was case-sensitive, and its own safety-net assert used the identical broken pattern — a file named _ATS_credentials_x.md would slip into the indexable set and the assert would still print "passed." Found independently by both reviewers. Fixed with a dedicated case/separator-insensitive regex, plus a second, content-based check — scanning actual chunk text for the word "password" — that shares no code path with the filename check. That second check immediately caught something real: RESUME_HERE.md and five other legitimately in-scope files had plaintext ATS passwords typed straight into their prose. Those 13 chunks are now quarantined at ingest — filtered out, never printed to a log, with a pointer to which file/section needs redacting.
  • job.json list fields were corrupted — Python's str(list) was embedding raw ['a', 'b'] repr syntax into `job_meta` chunks. Fixed: list/dict values now flatten to readable `"; "`-joined text.
  • HTML stripping fused adjacent words — <td>Acme</td><td>Corp</td> was coming out as one word, "AcmeCorp" — confirmed on a real resume, not just a synthetic case. Fixed: every tag boundary now inserts a space.
  • Italic-stripping could delete real content — a single unpaired asterisk (a salary footnote like $150k*) could pair with an unrelated later asterisk and silently erase everything between them. Removed italic-stripping entirely rather than patch an inherently ambiguous regex — bold stays (unambiguous, paired **), italics don't.
  • No fallback for non-job.json JSON files — would have crashed the whole run on any future stray .json file. Generalized to any .json.
  • Table-separator regex was one character too loose — it would have misread a genuine data row of this tracker's own "-" blank-value convention as a header separator and swallowed it. Tightened to require 3+ dashes per cell, the real markdown convention.

One scope bug too: this guide's own saved copy (career-rag-guide.html) is a top-level .html file sitting in the same folder — it was being classified as a master resume and indexed. Added to the out-of-scope list.

03

Pick the embedding model

Anthropic doesn't run an embeddings endpoint — Claude reads and writes text, it doesn't turn text into vectors. That step has to come from somewhere else. Decision made: zero ongoing cost wins over the last few points of quality — everything below runs on the author's own machine, no API key, no credits, no account to manage.

bge-small (local)chosen

Runs offline via sentence-transformers — one-time ~130MB model download, then every embed call is free and never leaves the machine. Slightly weaker semantic separation than the paid options on short professional text, but at ~90 folders that gap doesn't change which results surface.

Voyage voyage-3.5

Anthropic's recommended embedding partner, strongest quality on short dense professional text. Paid API — cents per batch, but a separate account and a separate credit pool from Claude usage. Not the path here.

OpenAI text-embedding-3-large

Comparable quality to Voyage, same problem — another paid account, another key. Ruled out for the same reason.

career_index/embed.py — kept separate from lib.py on purpose
MODEL_NAME = "BAAI/bge-small-en-v1.5"

def get_model():
    global _model
    if _model is None:
        from sentence_transformers import SentenceTransformer
        _model = SentenceTransformer(MODEL_NAME)
    return _model

def embed_texts(texts):
    vectors = get_model().encode(list(texts), normalize_embeddings=True)
    return [v.tolist() for v in vectors]

Steps 1+2 (lib.py) stay pure stdlib on purpose — no install needed to inventory or chunk. This is the one file where the sentence-transformers dependency enters, isolated in its own career_index/.venv.

04

Pick the vector store

At 90 folders and a few hundred chunks total, this is a small-data problem — the deciding factor is operational overhead, not scale.

Chromarecommended

Embedded, persists to a local directory, no server to run. Drops straight into the existing Python pipeline next to tailor.py. Right choice at this scale.

LanceDB

Also embedded and local, columnar under the hood — faster at millions of rows. No benefit yet at a few hundred chunks.

Qdrant / pgvector

Both want a running server or a Postgres instance. Only worth it if this becomes a shared, multi-user tool — not for one person's job search folder.

career_index/store.py — id collision caught on the first real run
def _chunk_ids(chunks):
    # NOTE: extra (section/row/part) alone isn't unique -- two different
    # _tracker.md sections can share a header title across batches. That
    # collided for real: 11 duplicate ids, chromadb.errors.DuplicateIDError.
    # A per-(path, doc_type) occurrence counter is what actually guarantees it.
    seen = {}
    ids = []
    for c in chunks:
        group_key = f"{c.path.relative_to(lib.ROOT)}:{c.doc_type}"
        n = seen.get(group_key, 0); seen[group_key] = n + 1
        ids.append(sha1(f"{group_key}:{n}:{c.extra}"))
    return ids

05

Design the metadata schema

The text similarity search finds relevant chunks; the metadata is what lets you filter and rank them ("only Applied roles", "only Australia", "only Finance sector"). The original plan here was wrong in one specific way, worth stating plainly: it assumed job.json held structured JD fields like location and salary. Building it for real showed job.json is actually tailor.py's template input (profile paragraph, competency bullets) — no location, no salary, no sector. That data lives in _tracker.md rows instead, joined onto each folder by matching company names (camelCase-aware folder-name fallback when a folder has no job.json) — and two fields the author asked for early on, country and category, don't exist as structured data anywhere, so they're regex/keyword extractors over NOTES.md prose, not lookups.

company, role from job.json, folder-name fallback platform, salary, status, sector joined from the matching tracker row — scored match, not first-match-wins country tracker's Location column when it resolves to one, else a keyword scan over NOTES.md category tracker's own Sector column when present, else a keyword scan contact_name first segment of the tracker's Hiring contact field doc_type, path, section/row/part from chunking (steps 1–2), always wins over folder-level fields
career_index/meta.py — scored join, not first-match-wins
def _match_score(key, rc):          # key = folder's company, rc = tracker row's Company
    if key == rc: return 100                                    # exact
    if len(key) >= 6 and (key in rc or rc in key): return 80    # substring
    overlap = significant_words(key) & significant_words(rc)    # generic words
    if overlap and len(overlap)/min(...) >= 0.6: return 50+     # (group, engineer,
    return None                                                 #  senior...) excluded

# take the BEST-scoring row, not the first one found; a tie among
# word-overlap-only matches (score < 80) is genuinely ambiguous between
# two different companies -- refuse rather than guess
gap, not built
"How long has the job been open" — genuinely not buildable from this corpus. job.json's date field is when the application was tailored, not when the role was posted — the original posting date was never captured for any of these 90 folders, so a days_open field can't be backfilled retroactively. Buildable going forward only: capture the posting date at scrape time for every new batch, then compute the age live at query time (never store it statically, per the earlier note on this field).

audited — round 2
Two more independent reviews, same cross-check pattern. Both agents independently reproduced the same critical failure: the company-name join was matching on generic shared words ("group", "engineer") and taking the first hit instead of the best one — Automic Group, Georgiou Group, Nuage Technology Group, and Macquarie Group were all silently joined to Professional Search Group's tracker row — and PSG's own folder never got its own data. This is worse than a missing match: it looks successful (_tracker_matched: True) while being wrong. Four fixes:
  • Rewrote the join as a scored match, not first-found. Exact/substring matches score highest and win outright; word-overlap matches exclude a stopword list of generic business terms (group, engineer, senior, solutions, search, partners...) and require 60%+ of the smaller company name's meaningful words to overlap. A tie between two different companies is now treated as genuinely ambiguous and refused, rather than guessed. Tracker-join coverage dropped from a fake 82% to an honest 68% — the right direction.
  • Status was being fabricated. Any matched row without an explicit Status column defaulted to "Applied" — including rows that live under the tracker's own "Skipped" and "blocked" sections, breaking the module's own headline use case. Fixed: status now comes from the row's _section title (Skipped / Blocked / Flagged / Applied) when there's no explicit column, defaulting to nothing rather than a guess.
  • Two real tracker headers were missing from the alias map — "Asked salary" (reversed word order from the aliased "Salary asked") and "Hiring contact (for reference)" — silently dropping real salary data for otherwise-correctly-matched folders. Rebuilt the alias map by enumerating all 14 real header tuples in the file instead of patching misses reactively.
  • Category/country keywords were firing on the author's own bio, not the target company. "visa" and "aemo/aer/arena" are the author's own past-employer references, reused near-verbatim in the "real fit" framing paragraph across dozens of unrelated NOTES.md files — mislabeling Deloitte and WWT as Energy. Removed both from the keyword lists.

One more found solo while re-verifying the fix: the camelCase folder-name splitter was breaking on acronym-style names — J4RVIS was splitting into "j4 rvis" because the splitter treated digit→uppercase the same as lowercase→uppercase. Fixed to only split at a real lowercase→uppercase boundary.

06

Write the ingestion script

By this point the real work already lives in store.build() — chunk (steps 1–2), embed (step 3), attach metadata (step 5), upsert (step 4). Step 6 is deliberately thin: one documented entrypoint that's the actual command to re-run after every batch, instead of "run store.py and ignore the test-query part at the bottom."

career_index/ingest.py
import store

def main():
    coll, chunks = store.build()
    print(f"\n{coll.count()} vectors in the store.")
    return coll.count()

if __name__ == "__main__":
    main()

Safe to re-run — chunk ids are stable (proven in the second audit round: byte-identical across repeated runs), so Chroma's upsert updates existing vectors and adds new ones without ever duplicating the whole store. Not assumed — run twice below.

08

Wire in live job matching

This is the second half of the ask — the store searching for jobs, not just searching what's already there. Every vibatchium batch run already scrapes new postings; the only addition is embedding each JD and comparing it against the resume + best-fit-precedent vectors before it reaches a shortlist. Dedup reuses step 7's fix — substring/text search over tracker_row + tracker_note, not a distance threshold — the earlier plan's dist < 0.08 idea would've missed the same prose-only mentions query.py's dedup check already had to be fixed for.

career_index/rank_new.py — tested against 3 real, live-scraped postings
resume_vec = average(coll.get(where={"doc_type": "resume_master"})["embeddings"])

for posting in postings:                          # from vb explore/research output
    already = search(tracker_row + tracker_note, for=posting.company)
    if already:
        skip()                                     # already in the tracker, any status
        continue

    jd_vec = model.encode(posting.text, normalize_embeddings=True)
    fit_score = cosine(jd_vec, resume_vec)
    precedent = top_3_similar(coll, doc_type="notes", to=jd_vec)
    write_row(posting, fit_score, precedent)        # → new_matches.md, ranked high to low

Tested against three postings actually scraped this session via vb explore — a real, currently-open Lorikeet FDE role, a Garvan Institute role, and a Salesforce FDE role (a company already in the tracker under three prior mentions). The dedup check correctly skipped Salesforce; the other two ranked, each with real precedent pulled from the corpus — Lorikeet's closest match was nDeva's NOTES.md, another Sydney AI-first startup, a genuinely apt comparison, not a coincidence of shared buzzwords.

audited — round 3
A third audit round (three agents this time) found the resume vector wasn't unit-length — a flat average of 5 chunks measured norm 0.907, not 1.0, silently deflating every fit score ~9% — and it was weighted by chunk count, not by resume variant (the 3-chunk Energy resume got 60% of the weight, the 2-chunk Principal FDE resume only 40%, contradicting the intent to compare against both equally). Fixed by averaging each variant's chunks first, then averaging the two variants, then renormalizing to length 1 — Lorikeet's score moved from 0.672 to the corrected 0.748. Ranking order was never affected (a constant scale factor doesn't change who's on top), but the absolute numbers were wrong.

audited — round 4
Three more agents this round found real, subtler problems — the earlier "5 companies genuinely have no folder" claim turned out to be wrong for one of them, and fixing that surfaced a deeper issue:
  • Talenza was falsely reported as having no folder — it has a real one (Talenza_AI_Delivery_Lead/). Root cause: this script normalized a folder-name fallback with plain _norm() instead of meta._norm_folder()'s camelCase splitter, gluing the folder name into one unsplit blob. Fixed to detect the fallback case the same way meta.py itself does.
  • Deeper root cause, found while re-verifying that fix: meta._norm() silently deleted punctuation instead of treating it as a word boundary — "Blackbook.AI" normalized to the single glued token "blackbookai", while the same company's folder name went through the camelCase splitter and correctly became two words. Same company, two incompatible tokenizations depending on which function touched it. Fixed at the source in meta.py — punctuation now becomes a space uniformly. Re-verified this didn't regress the second audit round's fix: Automic/Georgiou/Nuage still correctly stay unmatched, PSG still correctly keeps its own data.
  • A near-miss "needs review" pass caught its own tie-breaking bug before shipping — Talenza's real folder and an unrelated company (Insignia) tied at the exact same overlap score; keeping only the alphabetically-first "winner" would have pointed a human at the wrong company with false confidence. Fixed to show all tied candidates.
  • HIGH, in store.py — the round-3 client-caching fix traded one bug for another. Caching the Chroma client fixed the concurrency crash, but a long-running webui.py process kept serving stale data forever after a separate ingest.py run rebuilt the store — no error, no crash, just silently wrong results. Fixed with a generation marker file that build() touches after every ingest; get_collection() checks it (one cheap stat call) and only reconnects when it changes — cached in the common case, self-healing after a rebuild, no restart needed.
  • MEDIUM — webui.py's result-count field had no validation. ?n=abc, ?n=0, and ?n=-5 all 500'd — the HTML's min=1 max=20 only guards the normal form, not a hand-edited or old saved history URL. Fixed with a try/except and a clamp.

All fixes re-verified against a fresh full rebuild: safety nets still clean, round-2's cross-join fix still holds, rank_new.py unaffected, and the sent count reconciles exactly (17 + 4 orphaned = 21, matching the log precisely) for the first time this round.

# Chrome's --app mode does NOT quit when its last window closes --
# confirmed live: it keeps running with zero windows, forever.
# open -W (wait for exit) would never return. So this polls instead:

open -n -a Chrome --args --app=$URL --user-data-dir=$PROFILE_DIR
CHROME_PID=$(pgrep -f "Chrome --app=$URL --user-data-dir=$PROFILE_DIR")

while kill -0 "$CHROME_PID" 2>/dev/null; do
    sleep 2
    WIN_COUNT=$(osascript -e '... count windows ...')
    [ "$WIN_COUNT" = "0" ] && break
done
kill "$CHROME_PID"              # force-quit the lingering process
.venv/bin/python maintenance.py  # step 10, on close

A unique --user-data-dir per launch means the PID match can never confuse this window with any other Chrome window already open on the machine — verified by starting a second, unrelated Chrome instance mid-test and confirming the watcher only ever tracked its own.

audited — round 5
Two more agents tested the launcher and store.py directly against a real running window — one found the pipeline itself completely clean after all four prior rounds' fixes; the other found three real edges in the newest code:
  • The window-close detector could misfire on a transient AppleScript error. Confirmed live: repeated osascript calls against a real, still-open window intermittently threw Invalid index errors — the original version treated that empty result identically to a confirmed zero-window count, risking a premature force-kill mid-session. Fixed: an error/empty reading no longer counts as evidence of anything, and a real zero has to show up on two consecutive polls before it's trusted. Reproduced the exact flakiness re-testing the fix — one poll errored, the debounce absorbed it, the next real closure was still caught correctly.
  • Career RAG.command never checked whether maintenance actually succeeded — a crashed run still printed "Done." Fixed to check the exit code and say so if it failed.
  • store.py's batched upsert had no failure handling — if a later batch failed, earlier batches were already written to disk with nothing telling you the store was now incomplete. Not silent (the exception still propagates), but unhelpful. Fixed with a clear message: upsert overwrites by id, so re-running ingest is always the safe recovery, and now it says so.

Also confirmed clean by direct testing: the launcher's PID-matching (via each launch's unique --user-data-dir) never touched the user's own regular, already-open Chrome — tested side by side with a live, many-tab Chrome window throughout.
